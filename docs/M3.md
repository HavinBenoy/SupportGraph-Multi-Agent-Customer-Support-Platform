# M3 - Evidence-based voice latency

Goal: make the voice line answer faster **without** weakening grounding, citation validation, abstention, escalation, approvals, RBAC, tenant/student isolation, injection protection, barge-in or turn management. Nothing here changes a model, an embedding model, the database schema or the architecture. Every behaviour change has a test; every optimisation that could cost accuracy is **off by default**.

Read this first: **nothing in this document is a measured laptop improvement.** I (Claude) work in a browser sandbox with fake models; I cannot run Ollama, a microphone or your CPU. Section 9 separates what the sandbox proved (correctness, plumbing) from what only your laptop can prove (speed), and section 10 is the checklist to find out.

## 1. What your two real calls say

Same question, "What is the fee for the Python Full Stack course?", both answered with `fees-and-payments#1`:

| | call 1 (cold) | call 2 (warm) | difference |
|---|---|---|---|
| `stt_ms` | 562 | 560 | 2 |
| node `triage` | 3940 | 1673 | **2267** |
| node `route` | 0 | 0 | |
| node `knowledge` | 7007 | 4259 | **2748** |
| node `qa` / `finalize` | 1 / 2 | 0 / 4 | |
| `turn_ms` (graph, wall) | 11092 | 5958 | **5134** |
| `endpoint_to_reply_ms` | 11656 | 6518 | 5138 |

What reconciles and what does not:
* **STT + waiting = the gap between the two totals.** `endpoint_to_reply_ms - turn_ms` is 564 / 560 ms, i.e. exactly the transcription time. The 250 ms "complete sentence" grace period overlaps the STT (STT time counts towards it), so there is no hidden wait. Nothing is lost between the caller stopping and the graph starting.
* **Nodes vs the graph:** 3940+0+7007+1+2 = 10950 vs 11092 (142 ms unexplained) and 1673+0+4259+0+4 = 5936 vs 5958 (22 ms). That remainder is LangGraph/checkpointer work between nodes. M3 reports it every turn as `unaccounted_ms` instead of leaving it to subtraction. The first call's 142 ms is consistent with a first database connection.
* **The graph is 91-93% of the delay.** STT is 5-9%. VAD/endpointing is not in these numbers because they start at the endpoint.
* **Both** nodes were slower on the cold call, and both use the same Ollama model. A single model load would hit only the first model call, so cold start is more than one thing. I cannot split it from node timings (that was the limit of M3.0.1). I do not claim a cause from this data; section 2 lists the candidates and what each one would look like in the new counters.

### 1.1 "QA is ~0 ms" is correct, not a measurement bug
Citation validation does not live in the `qa` node. It runs **inside the knowledge node** (FAQ graph: `retrieve -> generate -> validate`, plus one citation regeneration). The `qa` node runs deterministic checks only (the LLM critic is off by default, `SG_QA_LLM_CRITIC=false`), so 0-1 ms is the right number. M3 makes the truth visible: `stage.validate` (the citation check) is reported under the knowledge node, and `qa` stays tiny.

### 1.2 Where a turn's time goes (code path, with the cost class of each step)
```
mic -> WebSocket -> VAD endpoint -> [grace wait, overlaps STT] -> Whisper (0.56 s) -> graph:
   triage      one structured-output model call (skipped by code for pleasantries, human requests, injection) .... LLM, ~1.7 s warm
   route       code ....................................................................................... ~0
   knowledge   rewrite (glossary, no model) -> embed question (Ollama) -> pgvector search -> build prompt
               -> grounded model call -> citation validation (+ one regeneration only for an UNCITED answer) .. LLM, ~4.3 s warm
   qa          deterministic checks ........................................................................ ~0
   finalize    code ....................................................................................... ~0
-> Piper (first sentence ~0.1 s) -> paced audio -> browser playback
```
Two model calls per FAQ question, on the same 1.7B model, sharing one CPU with Whisper, Piper and Postgres.

## 2. Cold vs warm: candidates, and how the new data tells them apart

| Candidate | Why it is plausible | What it looks like in the M3 data |
|---|---|---|
| **A. Ollama reloads the model because the warm-up used different options.** Ollama starts a new runner when the context size or thread count of a request differs from the loaded one. The old warm-up preloaded with `/api/generate` and *no* options; real calls send `num_ctx` (and now optionally `num_thread`). | Found by reading the code (`llm/preflight.py` vs `llm/gateway.py`). Fixed regardless: the preload now sends the same runner options (test: `test_the_preload_uses_exactly_the_options_the_real_calls_send`). | `llm[].load_ms` in the first real call of a turn is seconds, not milliseconds. |
| **B. The model was simply not loaded yet** (the API-start warm-up runs in the background, so a call made right after start can overtake it; Ollama then queues behind the load). | Normal. | Same as A: `load_ms` seconds. `cold_reasons: ["llm_load"]`. |
| **C. The embedding model loads on the first search.** | Warm-up loads it, but only if the warm-up finished or its options matched. | `stage.embed` of seconds on the first call; `cold_reasons: ["embed_slow"]`. |
| **D. Prompt (KV) cache.** llama.cpp reuses the longest identical prompt *prefix* held by a slot. Call 2 repeated call 1's question, so its triage prompt and its whole FAQ prompt were identical to call 1's and mostly cached. A **different** question would not get that help for the FAQ prompt. | Explains why the repeat is fast even when nothing is "cold". **It also means 6.0 s is the best case, not the typical warm case.** | `llm[].prompt_eval_ms` / `prompt_tokens`: a cached prompt reports few evaluated tokens and a tiny `prompt_eval_ms`. This is why the benchmark has both `warm_faq_repeat` and `warm_faq_varied`. |
| **E. Lazy initialisation** (database pool, tenant config, imports, checkpointer). | First call only; the 142 ms unaccounted on call 1 hints at some of it. | `unaccounted_ms`, `stage.search` and `other.*` high on the first run only; `first_run: true`. |

The two Ollama processes share a related trap: triage and the FAQ answer use **different prompts on the same model slot**. With one slot (`OLLAMA_NUM_PARALLEL=1`) each call overwrites the other's cached prefix, so neither benefits from the previous call of the other kind. This is a server setting, not code; see section 8.

## 3. What M3 implements

### 3.1 Instrumentation (`app/observability/stages.py`)
A `StageRecorder` per graph run (ContextVar; no-op without one), a `with stage("name")` timer, and an `OllamaMetricsHandler` callback attached to every Ollama chat model.
* Stages (all under the node that was running): `triage_llm`, `rewrite`, `cache_check`, `embed`, `search`, `context`, `llm`, `llm_retry`, `validate`.
* **No double counting:** stages are *inside* nodes and never overlap each other. For every node with stages the report gives `other = node_ms - sum(stages)` (DB-session setup, tenant config, graph overhead), so `node = stages + other` always holds (never negative). Across the run, `graph_ms = sum(node_ms) + unaccounted_ms`.
* Ollama counters per model call: `load_ms`, `prompt_tokens`, `prompt_eval_ms`, `prompt_tok_s`, `decode_tokens`, `decode_ms`, `decode_tok_s`, `total_ms`.
* Verdict: `cold` is true when a call's model load took `SG_OBS_COLD_LOAD_MS` (800) or more, or the embedding took `SG_OBS_COLD_EMBED_MS` (1500) or more, or it was the first run of the process and nothing had warmed it. `cold_reasons` says which.
* Privacy: names, numbers and flags only. A test asserts the question and the answer text are not in the report.

### 3.2 Four different latencies (voice session)
A holding phrase ("One moment please.") is audio, but it is never "the answer". M3 keeps them apart.

| Metric (in `timing`) | From -> to | Computed in |
|---|---|---|
| `stt_ms` | audio of the turn -> transcript | `VoiceSession._settle` |
| `endpoint_to_graph_done_ms` (= `endpoint_to_reply_ms`) | caller stopped talking -> the validated answer text exists | `VoiceSession._process` |
| `endpoint_to_first_audio_ms` | caller stopped talking -> first audio frame **of any kind** (holding phrase included) | `VoiceSession._speak` |
| `endpoint_to_filler_ms` | -> first frame of the holding phrase | `_speak` |
| `endpoint_to_answer_audio_ms` | -> first frame of the **answer** | `_speak` |
| `endpoint_to_playback_done_ms` | -> the answer has finished playing (the browser's `ended` ack, or the estimated end) | `_speak` |
| `endpoint_to_first_audible_ms` / `endpoint_to_answer_audible_ms` | -> the browser says the first sound (any / the answer's) is audible. Includes the network hop. Only when the browser acks. | `VoiceSession.playback_started` |
| `tts_first_ms` / `tts_first_filler_ms` | start of speaking -> first synthesised chunk (answer / phrase) | `_speak` |
| `turn_ms` | graph wall clock (`graph.invoke`) | `_process` |
| `nodes`, `stages`, `unaccounted_ms`, `llm_load_ms`, `cold`, `cold_reasons` | the graph breakdown above | `_process` from `out["perf"]` |
| `answer_audio_ms` | length of the answer audio actually sent | `_speak` |

`endpoint` is the end of the caller's last speech segment (`Turn.last_endpoint`); typed turns have no endpoint, so they have no `endpoint_*` metrics.
Where to read them: the `reply` message (`timing`, graph part), the `audio_end` message (`timing`, per response), the **`metrics` message** (once per fully spoken answer, sent just before that response's `audio_end`), the `graph_done` / `latency` / `turn_latency` / `playback_audible` voice events, and the browser DevTools -> Network -> WS -> Messages. A holding phrase has no `metrics` message; an interrupted or stale answer reports none.

### 3.3 Model lifecycle (`app/llm/warmup.py`, `app/llm/preflight.py`)
Sequential, in one background thread, once per process, never blocking a request or the event loop, each step independent:
1. **Ollama preload** of every chat model and the embedding model with the **same runner options as real calls** (`num_ctx`, `num_thread`; `num_predict: 1` for the preload only).
2. **Triage prime**: one real structured triage call on a fixed synthetic sentence (allocates the KV cache, builds the JSON grammar). Not cached, not counted as a turn.
3. **Retrieval prime**: one embedding call and one `SELECT 1` (HTTP connection, DB pool).
4. **Voice** (voice page only): Silero, one Piper synthesis, one second of Whisper silence, then pre-render the fixed holding phrases (3.7). Waits for steps 1-3 so two loads never compete for the CPU.
A failed step is reported (`/api/voice/status` -> `warm_detail`), logged and does not stop the others or crash anything; a failed LLM warm-up leaves the process "not warmed" (so the first turn is honestly marked cold). Instances are reused (`_components`, the gateway factories); nothing is loaded twice. Fake providers: no-op (state stays `null`).
API start-up starts steps 1-3 (as the old warm-up did, now complete); the voice status call starts 4.

### 3.4 Triage
* **Cache** (default on, 256 entries, 1 h): same normalised message text -> same classification, no model call. Only a *successful* model answer is stored; a provider error or invalid output yields the safe low-confidence result for that one call and is never stored. The cache holds a classification only; routing, `decide_route`, the escalation floor, the injection screen and authorisation run after it on every call (tests: a cached "wants my own records" classification routes anonymous callers away and signed-in students to the action branch; a cached entry never beats the floor or the injection screen; an outage is not remembered).
* **Compact prompt** (`SG_TRIAGE_PROMPT=compact`, **off**): about 40% fewer prompt characters, same schema and rules (a test checks every category and the injection rule are still in it). It needs `make eval-routing` with your real model before you switch it on: routing quality outranks speed.
* **`SG_TRIAGE_MAX_OUTPUT_TOKENS`** (**off**, 0 = global cap): the JSON answer is short, so a cap of ~160 only guards against runaway output; it does not speed up a normal call.
* Already true and unchanged: pleasantries, goodbyes and explicit human requests are decided by code with **no** triage call; the injection screen and escalation floor still run. I did **not** add keyword shortcuts for ordinary questions: a code rule cannot replace the classifier without risking intent, auth and escalation handling.

### 3.5 Knowledge
* **Validated-answer cache** (default on): section 5.
* **Prompt-size controls** (**off**): `SG_RAG_CONTEXT_BAND` keeps only passages within that score distance of the best; `SG_RAG_MAX_CONTEXT_CHARS` caps the passage text sent. The best passage is always kept and passages are never cut. A dropped passage cannot be cited (the validator only knows the passages that were sent), so trimming can only turn an answer into an abstention, never into an ungrounded answer (test). **They can drop the passage that holds the answer, so they are off until the benchmark's `context_top_k_*` scenarios and `make eval-rag` show your questions still pass.**
* Stage timings for embed / search / context / llm / validate (3.1). `rag_top_k` (existing, 4) is the other lever; the benchmark compares 1-4.

### 3.6 CPU awareness
* `SG_LLM_NUM_THREAD` (**unset**): pins Ollama's CPU threads for chat calls and the preload together (they must agree or Ollama reloads). Your i5-11300H has 4 physical cores / 8 threads; Ollama picks its own default (usually based on the physical cores). Try 4 vs unset with the benchmark; do not assume more threads is faster (hyper-threads share a core's units, and Whisper/Piper/Postgres share the CPU).
* Warm-up is sequential and the voice load waits for the LLM load (no two loads at once).
* `SG_VOICE_STT_THREADS` (existing, 4) and Whisper/LLM contention: Whisper runs *before* the graph for a turn, not during it, so they do not compete inside one turn; they can overlap only across turns (a new utterance while the graph runs).
* The benchmark samples system CPU busy % and free memory per run (`/proc`), so oversubscription shows up as CPU saturation without throughput gain.
* Memory: chat model (~1.4 GB) + embedding model (~0.3 GB) + Whisper base.en (~0.3 GB) + Piper + Postgres fit comfortably in 16 GB; nothing in M3 loads another copy of a model.

### 3.7 Voice experience
* The configurable holding phrase (`SG_VOICE_FILLER_AFTER_MS`, 1800; 0 = never) is unchanged: none for fast replies, never overlaps the answer (one speak lock), interruptible, cancelled by barge-in or a newer question; the answer is spoken only after validation.
* **New: fixed holding-phrase audio is rendered once per speech engine and replayed** (`SG_VOICE_CACHE_FILLERS`, true). The phrase is spoken at the moment the LLM is using the CPU; rendering it again then slows both and delays the phrase. Only the three fixed phrases are ever cached (keyed by the engine object); answers are always synthesised fresh; a phrase cut while being rendered is never stored (tests).
* **"Safe post-validation chunking" already exists and was kept:** the validated answer is split into sentences and Piper renders sentence 1 while the paced sender streams; first audio waits for one sentence, not the whole answer. Streaming *unvalidated* text is not done and will not be.
* New browser ack `{"type":"playback","turn_id":N,"state":"started","filler":bool}` when the first sound is audible (scheduled on the audio clock, not on receipt). It is optional for old clients.

### 3.8 STT
About 0.56 s = 5-9% of a turn. No evidence justifies changing the model or beam (`SG_VOICE_STT_BEAM`, 1, already exists). Not touched. A larger model is not introduced.

## 4. Optimisations deliberately NOT implemented
| Idea | Why not |
|---|---|
| Run the question embedding in parallel with triage | Saves one embedding (tens of ms warm); on 4 cores the two would contend, and the result is wasted whenever the route is not knowledge. |
| Skip triage by keywords for "fee"/"course" questions | Brittle; would bypass intent, auth and escalation classification. Explicitly ruled out. |
| Stream the model's tokens to TTS | Would speak unvalidated text. Ruled out. |
| Raise `OLLAMA_NUM_PARALLEL` or add concurrency in code | Not safe blindly on 16 GB/4 cores; only measurable by you (section 8). |
| Switch/shrink the model, change the embedding model | Ruled out without strong evidence. |
| Reduce Whisper accuracy | 0.56 s is not the bottleneck. |
| Cache answers for signed-in students or anything non-FAQ | Isolation risk; default is anonymous only. |
| Pre-render *answers* | Answers depend on documents and the caller; only fixed phrases are cached. |
| Lower `num_ctx` by default | A real lever (`SG_LLM_NUM_CTX`, existing) but it changes truncation behaviour; measure first. |

## 5. Caching: what, when, how it is invalidated, and is it worth it
**What:** the finished knowledge result for one question: the answer, the cited passages and the queries. **Where:** in memory, per process, per graph (a new graph starts empty; a restart empties it). **Size/TTL:** 128 entries (LRU), 30 minutes.

**Eligible only if all hold:** caller anonymous (`SG_ANSWER_CACHE_ANONYMOUS_ONLY=true`); route `knowledge` (the injection screen, the escalation floor, conversation intents and every other route never touch it); the result is a full validated answer (not abstained, reason `answered`, at least one citation, every citation among the stored passages, no sentinel). Never stored: abstentions, truncated/uncited/declined answers, "model unavailable" fallbacks, anything produced after an error. The knowledge graph must be the one built from settings (an injected graph may use another embedder, so no cache).

**Key:** tenant + normalised question (case, spacing and trailing punctuation only) + a fingerprint of the tenant's ingested documents (doc ids, content hashes, passage count for the embedding model) + a fingerprint of the settings that change an answer (models, temperature, seed, context size, retrieval and prompt-size settings, retries, rewriter). The question used is the **resolved** one (M2.2 follow-up/correction text), so "Are there any discounts?" after a Python question and the same words after a Java question never share an entry.

**Invalidation:** the document fingerprint is recomputed from the database on **every lookup**, so re-ingesting a changed or removed document changes the key and the old answer can no longer be found (tests: edited document hash, deleted passages); entries expire; the cache is bounded. If the fingerprint cannot be computed (database trouble) the normal path runs.

**On a hit:** the stored answer is validated again with the FAQ graph's own citation rule (a failing or tampered entry is dropped); the result then goes through the QA node and finalize exactly like a fresh answer (sample-notice included), and the answer is spoken only after that. A returned entry is a copy; callers cannot alter the stored one.

**Is it worth it? Honestly: only for exact repeats.** The triage cache (same text) is separate and saves the triage call (1.7 s warm in your trace); the answer cache skips embed + search + prompt + the model + validation, i.e. nearly all of the knowledge node (4.3 s warm). Its value is the **repeat rate** of identical questions among anonymous callers, which I cannot know; a call centre asking about fees, timings and placements probably repeats, a free-form assistant would not. The cost is ~2 ms for the fingerprint query and a bounded amount of memory, and the risks are mitigated above, so it is on by default; it can be switched off (`SG_ANSWER_CACHE_SIZE=0`), and `bench-voice --no-cache` shows the honest uncached numbers. It does **not** help varied questions at all.
Evaluations (`app/evals/run.py`, `make eval-routing`) switch both caches off so they measure every model call.

## 7. Benchmarking (`make bench-voice`)
The same questions through the whole support graph with stage timings, Ollama counters, cold/warm verdict, cache hits and CPU/memory. Needs `make db-up db-setup ingest` and, for real numbers, `SG_LLM_PROVIDER=ollama SG_EMBEDDING_PROVIDER=ollama` in your `.env`.
```
make bench-voice ARGS="--no-cache --n 10 --label before"          # honest per-call numbers; copy the file it writes
# ... change ONE thing (a setting or the code), restart nothing else ...
make bench-voice ARGS="--no-cache --n 10 --label after"
make bench-voice ARGS="--compare ../evals/bench-voice/before-....json ../evals/bench-voice/after-....json"
make bench-voice ARGS="--cold"                                    # adds a TRUE cold first call (unloads the Ollama models first), 3 runs
make bench-voice ARGS="--scenarios warm_faq_repeat,warm_faq_varied --n 20"      # enough runs for P90/P95
```
Scenarios: `cold_first` (needs `--cold`), `warm_faq_repeat` (same question: best case, shows cache and prompt-cache effects), `warm_faq_varied` (8 different questions: the realistic warm case), `unsupported` (abstentions), `human_escalation` (code path, no model), `greeting`, `long_utterance`, `context_top_k_1..4` (different retrieved-context sizes). Statistics: n, mean, median, P90 (needs >= 10 runs), P95 (needs >= 20), min, max, separately for `all`, `warm`, `cold`, `cache_hit`. The JSON in `evals/bench-voice/` keeps every run. Same procedure before and after = same command, same machine, same documents (the settings snapshot of both files is printed so a mismatch is visible).
It measures the graph path. Speech-to-text and Piper: `make bench-stt`, `make bench-tts`. End-to-end voice numbers: the `metrics` message of a real call.

## 8. Troubleshooting
* **First call after start is slow:** `curl localhost:8000/api/voice/status` -> `warm_detail`. `llm: "running"` = still loading, wait; `failed` = see the `steps` error and the API log ("warm-up step ... failed"). Then check the turn's `cold_reasons` and `llm_load_ms`.
* **`llm_load_ms` is seconds on a call that should be warm:** the model was unloaded or reloaded. Run `ollama ps`: both `qwen3:1.7b` and `nomic-embed-text` should be listed with `UNTIL` ~30 min away. If one is missing, Ollama evicted it (memory pressure, or `OLLAMA_MAX_LOADED_MODELS` too low): raise it or close memory-hungry apps. If you changed `SG_LLM_NUM_CTX`/`SG_LLM_NUM_THREAD`, restart the API so the preload uses the new values.
* **Slow triage** (`stage.triage_llm` > 2 s warm): look at `llm[].prompt_eval_ms` vs `decode_ms` for role `triage`. Prompt-bound -> try `SG_TRIAGE_PROMPT=compact` after `make eval-routing`. Decode-bound -> the JSON is ~45 tokens; check CPU contention (`cpu_busy_pct`) and thread settings.
* **Slow retrieval** (`stage.embed` or `stage.search` > 300 ms warm): embed slow = the embedding model was evicted (see `ollama ps`); search slow = the pgvector index/DB (check `docker compose ps`, `EXPLAIN` on the search).
* **Slow answer** (`stage.llm` > 3 s warm): `prompt_tokens` large and `prompt_eval_ms` dominant -> fewer/shorter passages (`context_top_k_*` scenarios, `SG_RAG_TOP_K`, then `SG_RAG_CONTEXT_BAND`/`SG_RAG_MAX_CONTEXT_CHARS`, each checked with `make eval-rag`). `decode_ms` dominant -> the answer is long; the prompt already asks for short ones. If triage and answer alternate on one model slot, `prompt_tokens` stays high for both: set `OLLAMA_NUM_PARALLEL=2` for the Ollama server only if you have the RAM (each slot reserves KV memory), and measure.
* **`other.knowledge` / `unaccounted_ms` large:** time outside any model or search: DB session setup, checkpointer writes (Postgres), tenant config. Run the benchmark with `SG_CHECKPOINTER=memory` once to compare.
* **Holding phrase late or missing:** `endpoint_to_filler_ms` in `audio_end`; the phrase is only spoken when the graph takes longer than `SG_VOICE_FILLER_AFTER_MS` and the caller is not talking. Piper slow? `make bench-tts`.
* **`endpoint_to_first_audible_ms` missing:** the browser ack did not arrive (old page; hard-refresh), or the response was cut first.
* **"Task was destroyed but it is pending":** fixed in M2.2.2; `test_paced_playback_leaves_no_stray_tasks_behind` guards it and still passes. If it ever reappears, it is a regression: send the log.

## 9. Performance report
**Sandbox (fake models, Postgres 16, CPU shared with the tooling).** These numbers prove the *plumbing*, not speed; the fake model answers in microseconds.
* The recorder survives LangGraph's worker threads, the stages of every node are recorded, node + other + unaccounted reconcile (tests).
* Answer cache: first anonymous FAQ question 197 ms (cold database connection, miss, stored), the next three identical ones 12-14 ms (hits). The 185 ms difference is the fake model plus a first-connection cost; it says nothing about Ollama.
* Benchmark runner, statistics, cold/warm grouping, comparison and the table were run end to end (`make bench-voice` against the sandbox database, fake providers; the output states "MODELS: FAKE").
* Suites (final run on the shipped tree): SQLite 1390 passed / 30 skipped; PostgreSQL 1418 passed / 2 skipped (the 2 need a real Ollama); frontend 60 passed, `tsc` clean; a run with numpy hidden (the optional-voice case) passes the non-voice suites (1019 passed / 2 skipped).

**Expected on your laptop, with the reasoning (not measured, do not quote as results):**
1. First call: the warm-up now preloads with the options real calls use and primes triage + retrieval, so `load_ms` of the first real call should be milliseconds if candidate A or B was the cause. If the gap persists, the counters will name the stage (section 2).
2. Repeated anonymous FAQ: skips ~4.3 s of knowledge work (embed, search, prompt, model, validation); expect about STT + 0.1 s.
