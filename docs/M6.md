# M6 - Knowledge store, document versioning and audit

One change set (`supportgraph-m6-complete.zip`). Migrations **0009** and **0010** (both additive; 0010 is the processing-ownership fix, section 4a). No new dependency, no model or embedding change, no second vector database, `.env` untouched, nothing deleted.

## 1. What M6 adds and what it does not
M6 puts a **managed knowledge store in front of the existing RAG index**. Administrators create documents, save every edit as an immutable version, process (chunk + embed) a version, review it and publish it. Publishing copies the processed passages into the **same `documents` + `chunks` tables the assistant already searches**, in one transaction. Nothing else is searched, so there is exactly one RAG pipeline.

Not changed: retrieval, chunking, the embedding model (`nomic-embed-text`, 768 dimensions), the answer cache logic, the FAQ/triage/escalation graph, calls, trial mode. Not built: a full management UI (M7), PDF/DOCX upload, student-only documents, scheduled publishing.

## 2. Concepts kept apart
| Concept | Where it lives | Meaning |
|---|---|---|
| Logical document | `kb_documents` | identity, title, category, tags, description, status `draft | published | archived`, `latest_version`, `published_version`, `row_version` (concurrency token) |
| Version | `kb_versions` | **immutable** content snapshot: number, text, checksum, size, source file name/type, created by/at, change note, `restored_from` |
| Ingestion state | `kb_versions.status` + `processed_at`, `processing_error`, `chunk_count`, `embedding_model` | `draft -> processing -> ready | failed`; `processing_attempt` is the ownership (fencing) number |
| Publication state | `kb_documents.published_version` + version status `published / superseded / archived` | which version is live |
| Staged passages | `kb_version_chunks` | processed passages of a version that is not live. **Never searched.** Exist exactly while a version is `ready` |
| Live passages | `documents` + `chunks` (existing) | what retrieval reads. `documents.kb_version` records which version they came from |
| Proposal | `kb_proposals` | one per approved feedback record; links feedback -> draft version; proposer / reviewer / publisher |
| Audit | `kb_events` | append-only trail |

Lifecycle words shown to people: **Draft, Processing, Ready for review, Published, Failed, Archived** (plus *Superseded* for an old published version).

## 3. Version rules
- A version is never edited or deleted: ORM guards raise on update of any content column and on delete; no HTTP route can do either.
- Every change (text or title) is a **new version**. Metadata (category, tags, description) is document-level and changes through `PUT`, with its own audit event.
- **Restore** creates a new version with the old text and title (`restored_from` set). v1 -> v2 -> v3 -> restore v1 = v4; v1-v3 are untouched. Restoring text identical to the latest version is refused (409).
- A version identical (checksum) to the latest is refused (409). The same text under another document id is allowed with a warning.
- Version numbers come from a compare-and-set on `kb_documents.row_version`; concurrent writers get distinct consecutive numbers (the server retries a few times; a caller who passes `expected_row_version` gets 409 instead).
- Checksum = SHA-256 over title + normalised body (CRLF -> LF). On publish it becomes `documents.content_hash`, which the answer cache already uses as its fingerprint, so **cached answers from the previous text can never be served**.

## 4. Processing, publishing, archiving
1. **Process** (`POST .../versions/{n}/process`): claim the version (CAS to `processing`, `processing_attempt + 1`; a claim older than `SG_KB_PROCESSING_STALE_S` can be taken over) -> chunk and embed **outside any transaction** with the same embedder retrieval uses -> in one transaction complete or fail the attempt (section 4a). A failure marks the version `failed` with a short non-sensitive reason and removes its staged rows; the published version is untouched. Processing again is safe: an unchanged `ready` version returns `unchanged: true`; `force: true` rebuilds.
2. **Publish** (`POST .../versions/{n}/publish`): only a `ready` version of a non-archived document, with the same embedding model it was processed with, and (if it came from feedback) only after its proposal is `approved`. One transaction: CAS on the document, delete the old live document+chunks, insert the new ones from staging, mark the old version `superseded`, the new one `published`, clear staging, write the audit event. Any failure rolls the whole thing back and the previous version stays live. Publishing the already-live version is a no-op.
3. **Unpublish**: removes the live passages; the document returns to `draft`; history kept; the version needs processing again before it can be published.
4. **Archive**: removes retrieval, keeps all history; no new publishing while archived. **Unarchive** returns to `draft`; nothing becomes live without an explicit publish.
5. Concurrent publishes: the compare-and-set takes the row lock (PostgreSQL) or loses the race (SQLite); exactly one live version remains and the loser gets 409.

### 4a. Processing ownership (fencing token, migration 0010)
**Problem (confirmed by tests against the previous code).** Embedding runs with no transaction held, so a slow worker A can outlive its claim: after `SG_KB_PROCESSING_STALE_S` worker B legitimately takes the version over. The previous completion/failure writes were guarded only by `status = 'processing'`, which cannot tell A from B. Reproduced: (1) A finishing while B was still embedding committed A's result as `ready` (B then lost); (2) A *failing* while B was embedding turned B's live claim into `failed`; (3) A failing after B completed deleted B's staged chunks (the delete was unconditional) while the version stayed `ready` with nothing staged, and A reported `failed`; (4) archiving a document during processing left the version stuck in `processing` until the stale timer. (A finishing after B had already completed was already refused, by accident of the status.)

**Fix.** `kb_versions.processing_attempt` is a monotonic fencing token, incremented by every claim (read back in the claim's own transaction). Every transition that ends an attempt is a compare-and-set on `status = 'processing' AND processing_attempt = <my number>`, executed **first** in its transaction (on PostgreSQL that UPDATE takes the row lock and re-checks the condition after waiting; SQLite serialises writers), and the staged-row writes/deletes and the audit event happen only if that UPDATE matched one row. A worker that lost ownership gets HTTP 409 ("processing was superseded by a newer attempt"), commits nothing but one `ingestion_superseded` audit event (its attempt and the current attempt), and can neither complete, fail, delete, nor overwrite anything. Archiving mid-processing now ends the attempt cleanly as `failed` ("archived while it was being processed"). Audit events carry `attempt`, so `ingestion_started/completed/failed` always describe the attempt that really did it.

**Why this and not the alternatives.** A random claim token would also isolate workers but is not ordered, so audit and diagnostics could not say which attempt is newer. Lease renewal (heartbeats) only reduces how often takeovers happen; it still needs a fencing check at commit, adds a writer thread and a new failure mode (a stuck heartbeat keeps a dead claim alive), so it is not needed for correctness. Row locks held across embedding would keep a transaction open for minutes and block publish/archive. The attempt counter reuses the compare-and-set style already used everywhere in M6, is identical on SQLite and PostgreSQL, adds one column, and recovery is unchanged: a crashed worker's claim simply becomes stale and the next claim increments the number, fencing the dead worker if it ever wakes up. A slow-but-alive worker whose result is discarded costs only CPU time; raise `SG_KB_PROCESSING_STALE_S` above your slowest realistic embedding run to avoid that.

## 5. RAG integration (the existing pipeline)
- Live passages carry `doc_id` and, through `documents.kb_version`, the version; `RetrievedChunk.doc_version` and the `"version"` key of a citation dict expose it. Disk articles have no version (field omitted).
- Retrieval itself is unchanged (tenant, `audience='public'`, embedding model). Drafts, ready-but-unpublished, failed, superseded and archived content is simply not in `chunks`.
- Re-processing never duplicates: staged rows are replaced per version, live rows are replaced per document.
- Embedding model or dimension changes are blocked at publish ("process it again"); there is no second index.
- **Disk ingest coexistence**: `ingest_tenant` skips documents that exist in `kb_documents` (listed in `IngestReport.managed_skipped`) and never withdraws them. `POST /api/admin/knowledge/import-disk` brings the disk articles under the store as `imported` documents (published v1, same chunks, nothing re-embedded differently); it is idempotent.

## 6. Feedback integration
`GET /feedback` lists intervention feedback with review status `approved_for_update` (read-only; the M4.1/M5 rows are never written). `POST /proposals` turns **one** such record into a **draft** (a new document, or a new version of an existing one) with text **the administrator writes** (the feedback text is only a reference). Then: process -> `POST /proposals/{call_id}/review` (approve / reject) -> publish, each an explicit human action. A proposal-linked version cannot be published while the proposal is `proposed` or `rejected`; publishing marks it `published` and records `published_by`. One proposal per feedback record (primary key; concurrent attempts leave exactly one). `SG_KB_REQUIRE_SEPARATE_REVIEWER=true` forbids the proposer from reviewing their own proposal (default off so a single-admin development setup works). **Approved feedback is permission to start an update, never permission to publish one.**

## 7. Audit
`kb_events` is append-only (ORM guards, no write routes). Actions: `document_created, metadata_updated, version_created, version_restored, ingestion_started, ingestion_completed, ingestion_failed, ingestion_superseded, version_published, version_unpublished, document_archived, document_unarchived, proposal_created, proposal_approved, proposal_rejected, disk_import`. Each row: tenant, actor, action, resource, document, version, time and a summary restricted to an **allow-list of scalar keys** (field names, counts, model name, status words, checksum, call id, a safe error class, the processing attempt number). Document text, titles, notes and feedback text cannot be stored whatever a caller passes. Failed requests write nothing.

## 8. Content and source handling
Text only: Markdown or plain text, sent as JSON (`content`). Optional `source_filename` (`.md`, `.markdown`, `.txt`; reduced to a safe base name, never used as a path) and `source_mime` (`text/markdown`, `text/plain`, must match). Limits: `SG_KB_MAX_BYTES` (200000) and `SG_KB_MAX_CHUNKS` (300), checked **before** anything is embedded. Refused: empty text, text with only a title, control characters, a leading `---` front matter block (the title/category/tags are fields), invalid ids (`^[a-z0-9][a-z0-9-]{0,127}$`), unknown categories, more than 10 tags. Content is stored in the database; no file is written, so a published source can never be overwritten. Unknown JSON fields are rejected (422), so no state can be smuggled in.

## 10. Security
Admin-only writes; staff read-only on published text; students excluded; tenant from the token, never from the request; every lookup includes the tenant (cross-tenant ids return 404, and the same id may exist in two tenants); ORM-enforced immutability of versions and the audit trail; unknown JSON fields rejected; strict integer/boolean types; parameterised SQL only; search wildcards escaped; transactional publish; concurrent-publish safety; no document or feedback text in audit, logs or error messages (processing errors are class names or our own refusals); no external service: embedding runs on the same local model as retrieval.

## 11. Database (migrations 0009 and 0010)
Adds `documents.kb_version` (nullable) and tables `kb_documents`, `kb_versions`, `kb_version_chunks` (embedding `vector(768)` on PostgreSQL, JSON on SQLite), `kb_proposals` (FKs to `intervention_feedback` and `kb_versions`), `kb_events`, with named CHECK constraints (document status/category/origin, `(status='published') = (published_version IS NOT NULL)`, version status, positive version number) and indexes. Existing rows are not rewritten. `downgrade` drops exactly these. **0010** (down_revision 0009) adds one column, `kb_versions.processing_attempt INTEGER NOT NULL DEFAULT 0` (constant default: no rewrite, existing rows read 0; downgrade drops that column). Tested up -> down -> up on SQLite and PostgreSQL 16 with existing documents, chunks and calls preserved. Existing documents stay disk-managed until an administrator runs `import-disk`.

## 13. How M7 consumes this
M7 is the full UI over the same endpoints: a documents table (`GET /documents` with its filters and pagination), an editor that posts `POST /versions` carrying the loaded `row_version`, a diff view (`GET /compare`), a publish bar driven by `latest_status` / version `lifecycle` (show Publish only for `ready_for_review`), a review queue (`GET /proposals`, `/feedback`), an audit browser (`GET /audit`, cursor `before_id`) and an import wizard (`/meta.unmanaged_disk_documents`, `/import-disk`). Every refusal arrives as `{detail: "<sentence>"}` with 404/409/422 and is meant to be shown as is. The M6 `KnowledgeAdmin` tab is a deliberately small client of the same API (src/lib/api.ts `kb*` functions, src/lib/types.ts `Kb*`).

## 14. Known limitations
- Text only (Markdown/plain); PDF/DOCX extraction, file upload and images are not supported.
- Processing runs inside the request: a large document with a slow CPU embedder makes `process` slow (the limits cap this; the stale-claim take-over recovers from a crash and the attempt number stops the old worker from interfering; a worker that outlives the stale threshold loses its result, so set `SG_KB_PROCESSING_STALE_S` above your slowest embedding run). A background worker is a possible later step.
- The reviewer-separation rule is off by default and needs two administrator accounts when on.
- Publishing replaces the document's live passages wholesale; there is no partial/section-level publish and no scheduled publish.
- Unpublish and unarchive send a version back to `draft`; it must be processed again before publishing (the staged passages are not kept for a non-ready version).
- Archive/unpublish stop retrieval immediately. A previously cached validated answer is keyed by the document content hash, so it stops matching once the document is withdrawn or replaced.
- Verified in the sandbox with the offline hashing embedder; real `nomic-embed-text` vectors take the same code path but were not exercised here.
