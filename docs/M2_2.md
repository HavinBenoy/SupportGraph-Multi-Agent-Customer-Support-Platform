# M2.2 - Voice turn management, utterance aggregation, sequential playback

Goal: **one complete user turn produces one coherent assistant response, and only one response is ever spoken at a time.**
Nothing about models, retrieval, RBAC, approvals or escalation changed. No migration, no new dependency, no model change.

## 1. Root cause (found by reading the code and reproducing it before changing anything)
Your symptom ("the first half of my sentence is answered, then the second half, and both answers play together") has **two independent causes**, plus four contributing defects. VAD was only one of them.

| # | Where | What happened | Evidence |
|---|---|---|---|
| 1 | Browser player (`frontend/src/lib/voice.ts`) | `start()` reset the playback clock (`nextAt = currentTime + 0.05`) and never stopped sources already scheduled for the previous response. The server sends audio far faster than real time (Piper RTF ~0.04), so a whole answer is already scheduled in the browser when the next `audio_start` arrives. Two answers therefore **sound together**. `push()`/`end()` carried no turn identity, so a late chunk could not be told from a current one. | Reproduced with a fake `AudioContext`: response 1 scheduled 0.05-6.05 s, response 2 scheduled 2.05-5.05 s. Now a vitest regression test. |
| 2 | Server (`VoiceSession`) | Silero ends an utterance after `silence_ms` of quiet. **Every utterance was its own STT -> graph -> TTS turn.** A 0.8 s pause inside a sentence made two turns, two replies, two `audio_start` events. | Reproduced: 0.8 s pause -> 2 graph invocations, 2 replies, 2 `audio_start`. |
| 3 | Server | `speaking` ended when the bytes were *sent* (fast), not when they were *heard*. Barge-in, the echo guard and "is the bot still talking" were wrong for most of every answer. | code |
| 4 | Browser | Playback stopped on every raw `speech_start` (96 ms of VAD speech: a cough, a click, the bot's own echo) instead of waiting for the server's sustained barge-in decision. | code |
| 5 | Server | One shared `_cancel` event, cleared at the start of every `_speak`: a cancel could be erased, and "interrupted" belonged to the session, not to a response. | code |
| 6 | Server | Nothing checked staleness: every reply was spoken FIFO even if the caller had already asked something newer. | code |
| 7 | Graph | The knowledge branch only saw the last human message, so "Are there any discounts?" lost the course. | code |

Raising the silence timeout would only have hidden cause 2 (and made every answer slower); it would not have touched cause 1.

## 2. Design
```
mic -> AudioWorklet 16 kHz PCM16 -> WebSocket -> Endpointer (Silero) --segment--> Turn (segments merged while the caller is mid-sentence)
      transcribe the merged audio -> adaptive grace period -> finalized turn -> ONE runner -> run_turn (the shared support graph)
      -> speak only if the turn is still current -> paced TTS, framed with (turn id, seq) -> browser player (one response at a time)
```
**Aggregation** (`app/voice/turns.py`, `VoiceSession`). `silence_ms` stays at 600 (it was 700) and now only ends a *segment*. A segment joins the pending turn; the turn is committed after a grace period that depends on the transcript, and STT time counts towards it:
complete sentence 250 ms, one or two words 700 ms, unfinished ("... the", "and", a comma, "...", "I want to know about the course", "I have a question") 1600 ms.
Speech starting during the grace period holds the turn; noise (`too_short`) releases it; if speech resumes the audio of all segments is concatenated and **re-transcribed whole**, so Whisper sees the full sentence. A turn is sealed at `voice_max_turn_s` (30 s). Segment and transcript boundaries are kept (`segments`, `segment_ms`, `merged`) in events and in the `reply` message; no words or audio go to logs.

**One graph run at a time.** A single runner task, a bounded queue (`voice_max_pending_turns`, 3) and a lock around `run_turn`; `stats.max_concurrent_graph` proves it stays 1.

**One spoken response at a time.** `_speak` holds a lock; each response has its own cancel token; every binary frame is `uint32 turn_id, uint32 seq, PCM16`; the server paces the stream at about real time (`voice_pace_lead_ms`, 1500 ms ahead) so a cancel cuts audio the caller really hears, and `speaking` stays true until the audio has played out or the browser acks `playback ended`.
**Stale replies.** A reply is stale when a newer real question exists (ack/thanks/greeting/"hello?" do not count; a correction does) or the caller is still talking. A stale reply is still sent as text (`stale: true`) but never spoken. Hand-offs and approval/confirmation outcomes (`escalated`, `awaiting_staff`, `awaiting_confirmation`) are never stale: the caller must hear them. A goodbye ends the call only if it is not stale.
**Barge-in.** While the bot is audible the endpointer needs `voice_barge_in_ms` of speech; only then does the server send `interrupted{turn_id}`. The browser no longer stops on raw `speech_start`; it stops on `interrupted{turn_id}` and then ignores every later chunk of that response (and any response older than the newest one).
**Browser player.** `begin(turn)` stops everything else first; `push/end/stop` carry the turn; late events for a cancelled or older turn are dropped; natural drain sends `{"type":"playback","turn_id":N,"state":"ended"}`.
**Close.** `close()` cancels timers, speech and the runner, gathers them, and later sends are no-ops. (Found while testing: a sealed turn's timer was cancelled by the next turn - fixed, with a test; and a hand-off marked "not stale" could still be skipped by `_speak` - fixed, with a test.)

## 3. Conversation context (shared graph: text chat and voice agree)
`app/conversation/context.py`, applied in the `triage` node. It only rewrites the text that is **classified and retrieved with**; the injection screen, the escalation floor, RBAC, the action/write branches and QA still see exactly what the caller said. It adds at most five words, taken from the caller's own earlier question (looking back <= 3 usable messages, skipping pleasantries and anything that looks like an injection). New state fields: `resolved`, `context_kind`.
| Said | Becomes | kind |
|---|---|---|
| "What is the fee structure for Python Full Stack?" then "Are there any discounts?" | "Are there any discounts for Python Full Stack?" | follow_up |
| "What is the fee structure for Python Full Stack?" then "Actually, I meant Data Science." | "What is the fee structure for Data Science?" | correction |
| "What is the fee?" then "Actually, I meant Data Science." | "What is the fee for Data Science?" | correction |
| "I want to know about the course..." + "...duration and eligibility." (short pause) | one turn: "I want to know about the course duration and eligibility" | continuation (aggregation) |
| a question naming its own topic, or with no referential cue ("Where is the campus located?") | unchanged | - |
Deterministic and conservative: no model, no invented facts. If the knowledge base has no grounded answer the usual abstention applies.

What would you like to know?"; a *pending* confirmation or approval is still resolved before the graph, so "yes" there still means yes); "Okay, I think that's it." -> goodbye; "No thanks, you may proceed to cut the call." and "feel free to end the call" -> goodbye; "You can end the call it's file." -> goodbye; "Thanks for having me. ## 5. Configuration (all optional; defaults shown; `.env` is not touched)

If you still see a split sentence, raise `SG_VOICE_GRACE_INCOMPLETE_MS` (or `SG_VOICE_GRACE_SHORT_MS`) rather than `SG_VOICE_SILENCE_MS`. A complete sentence pays at most ~250 ms; this is *not* the M3 latency work.

## 6. Observability
`VoiceSession.events` (last 1000) and the log line `voice_event {json}` carry only ids, sizes and timings: `session_start`, `vad_speech_start`, `vad_endpoint` (segment, ms, merged, sealed), `vad_too_short`, `stt_done`, `stt_empty`, `grace`, `turn_final` (segments, segment_ms, audio_ms, merged, supersedes), `graph_start`, `graph_done`, `reply_stale`, `tts_start`, `tts_first_audio`, `tts_done`, `playback_start`, `playback_done`, `barge_in`, `speech_cancelled`, `overlap_prevented`, `turn_dropped_queue_full`, `session_close` (with counters: segments, merged_turns, graph_runs, max_concurrent_graph, stale_replies, barge_ins, overlap_prevented). Test: no transcript text or student id appears in events. To read them live: `grep voice_event` in the API log.

## 7. Protocol changes (see docs/M2.md)
Every turn event carries `turn_id`. `transcript` is sent twice per turn (`final:false` after STT, `final:true` when committed; the browser updates one line). `reply` adds `stale`, `turn{segments,audio_ms,merged,kind}`, `intent`, `context`. Binary audio frames: 8-byte header (`uint32 LE turn_id`, `uint32 LE seq`) + PCM16. New client message `{"type":"playback","turn_id":N,"state":"ended"}` (malformed acks are ignored). `interrupted` carries `turn_id` and `reason`.

## 8. What is and is not verified
Sandbox (fakes: scripted STT, tone audio, energy VAD, fake TTS; fake AudioContext in vitest): everything above, through the real FastAPI WebSocket route and the real shared graph. **Not tested here: a real microphone, speakers, echo, Silero/Whisper/Piper on real speech, or real browser audio timing.** Whether your pauses are covered by the default grace periods is a tuning question only your real calls can answer.
